Changed files and behavior:

- `astra/App/BrowserAuthenticationSessionHandler.swift` replaces any session with the same request UUID before starting its successor. The retained navigation/window-close closures capture the generation by value and the request/window weakly; they do not retain the `Session`, window controller or browser. Cleanup captures only the `BrowserWebSession`. Each callback rechecks generation, request identity and window identity against the live map. `cancel(_:)` also requires request-object identity, so a stale cancel cannot stop a replacement. Native `request.callback.matchesURL(_:)` remains the only URL matcher. Closing, canceling, replacing or completing retires the old session; private-session data cleanup runs on each terminal path and remains idempotent with window-close cleanup.
- `astra/Web/Navigation/BrowserController.swift` considers every main-frame destination for native callback matching, including a top-level navigation initiated by a subframe, as required by the AuthenticationServices callback contract. New-window callbacks are eligible only when the source is the main frame. When an auth browser creates a popup, its child `BrowserController` receives the auth retry/retention flag before the returned WebKit view can load. Authentication-session controllers do not retain request headers in the controller's failed-request/retry state; automatic connectivity retries are disabled for these sessions.
- `astra/Web/Navigation/BrowserAuthenticationPolicy.swift` validates the initial HTTP(S) URL, host characters, non-empty in-range port and a 16 KiB URL limit; it rejects URL user information, invalid header names/values, line breaks, duplicate case-insensitive names, browser-managed headers and oversized header sets. Allowed supplied fields, including `Authorization`, remain on the one initial `URLRequest`. Header values are not logged or copied into browser persistence, history, sync, or the offline-retry request state.
- `checks/task23-authentication-policy-check.swift` exercises the production initial-request and source/target-frame policy.
- `AppDelegate` registration/launch integration was reviewed and retained: it assigns the existing handler through `ASWebAuthenticationSessionWebBrowserSessionManager` before the task that restores normal windows, and skips ordinary restoration when AuthenticationServices launched the app for a request. No AppDelegate behavior or unrelated keyboard/menu integration changed.

Acceptance cases satisfied, with evidence:

- Request replacement and callback completion are scoped to the captured UUID generation, exact `ASWebAuthenticationSessionRequest` object and exact `BrowserWindowController`; production-policy checks cover removed sessions, replacement generations, request identity and window identity. A delayed callback from a retired session returns false and cannot complete the replacement.
- Native `ASWebAuthenticationSession.Callback.matchesURL(_:)` checks the requested custom scheme or HTTPS host/path. The code does not recreate scheme/host/path matching or accept wildcard callback URLs.
- WebKit callback checks follow Apple's rule to examine all main-frame URLs: main-frame destinations are eligible even when an iframe initiated a top-level navigation. A new-window destination is eligible only from a main-frame source. The production policy check covers main-frame URLs, main-frame popups, iframe-initiated top-level navigation and rejected iframe popups.
- The existing `ASWebAuthenticationSessionWebBrowserSupportCapabilities` in `astra/Special/Info.plist` already enables `IsSupported`, `CallbackURLMatchingIsSupported`, `AdditionalHeaderFieldsAreSupported`, and `EphemeralBrowserSessionIsSupported`. The initial request is loaded as provided by the AuthenticationServices request. `shouldUseEphemeralSession` continues to select a per-window nonpersistent `BrowserWebSession`; cleanup runs on close, cancel, replacement, completion and app termination. Non-ephemeral requests retain the existing normal WebKit data-store behavior.
- No website password/passkey is stored by Astra. Astra's Apple Account/sync credential path remains in `BrowserSync`; HTTP Basic/Digest challenges remain owned by task 13. Authentication headers remain only in the initial WebKit request. Auth browser controllers do not retain them in retry state or retry them on connectivity restoration.
- Apple documents the browser session handler, app-supplied initial headers, native callback matching, and ephemeral-session request on [ASWebAuthenticationSessionWebBrowserSessionHandling](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsessionwebbrowsersessionhandling), [ASWebAuthenticationSessionRequest.additionalHeaderFields](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsessionrequest/additionalheaderfields), [ASWebAuthenticationSessionRequest.callback](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsessionrequest/callback), and [ASWebAuthenticationSessionRequest.shouldUseEphemeralSession](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsessionrequest/shoulduseephemeralsession). Apple's callback contract covers main-frame URLs; the public callback object owns matching.

Credential/provider capability evidence and pending acceptance:

- Apple states that WebKit automatically handles WebAuthentication challenges when a browser uses `WKWebView`; therefore Astra keeps passkey ceremonies and OS/third-party-provider selection native. No `ASAuthorizationController` bridge, credential listing UI, credential manager, password store, or fake passkey flow was added. See [Passkey use in web browsers](https://developer.apple.com/documentation/authenticationservices/passkey-use-in-web-browsers) and [Password use in web browsers](https://developer.apple.com/documentation/authenticationservices/password-use-in-web-browsers). This documents the WebKit path on Astra's macOS and iOS targets; it does not prove that an arbitrary relying party or provider works in the currently signed app. OS, domain/capability and provider acceptance remains pending on both.
- The browser-only `ASAuthorizationWebBrowserPublicKeyCredentialManager` exposes/request browser-app passkey access. The all-relying-party browser capability uses Apple's managed `com.apple.developer.web-browser.public-key-credential` entitlement and account-holder approval. Astra has no such entitlement or approved signing capability. No manager access flow was added because Astra delegates WebAuthentication to WebKit and does not present a browser-owned passkey list. See [the entitlement documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.web-browser.public-key-credential). Its absence remains a signed-configuration gate for that browser-manager route; do not infer arbitrary-RP support from the WebKit challenge documentation alone.
- The app's checked entitlements contain Apple Sign In only (plus the pre-existing isolated private Web Push entitlement in its separate configuration); neither contains associated domains or the managed browser passkey entitlement. No relying-party domain is specified by this task, so no `webcredentials` domain was invented. Associated-domain requirements for a particular relying party and Apple's managed browser entitlement are distinct configuration paths; signed acceptance remains pending.
- Password AutoFill, passkey/third-party credential suggestions, and strong-password creation remain WebKit/OS UI paths with no Astra-owned credential capture. Source does not establish them as successful on either target. Test representative HTML password and passkey flows, system suggestions, provider selection, strong-password creation, user cancellation, ephemeral session behavior and returned WebAuthentication outcomes on macOS and iOS.
